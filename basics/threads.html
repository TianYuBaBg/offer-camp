Lesson 7 · Concurrency

Why is HashMap not thread-safe?

Because put is many steps, and two threads can step on each other between them.

Basicsconcurrency

01The idea

Think of it like thisTwo people writing on the same line of a notebook at the same time. Person A writes “5”, person B writes “7”. The last hand wins, and nobody knows what the first hand wrote.

A thread is one worker inside your program. Two threads can run at the same time. A race condition happens when two workers use the same data and the result depends on who is faster.

02Why HashMap is not safe

Look at what put really does. It is not one step:

  1. compute the hash,
  2. find the bucket,
  3. insert the node at the end of the line,
  4. increase size, and maybe resize the array.

Between any two steps, the other thread can change things. Real results:

  • Lost update — both threads write a new value, one is silently gone.
  • Wrong size — both increase size from the same old value.
  • Broken line — two threads insert at the same place, a pointer is overwritten, items disappear.
  • Infinite loop (JDK 7) — two threads resize at the same time and the links form a circle; then get spins forever and the CPU is at 100%.

JDK 8 changed the resize to keep the order, so the circle is gone. The data loss is not gone: JDK 8 is still not thread-safe.

03What to use instead

OptionWhen
ConcurrentHashMapMany threads read and write. Locks only the bucket head, so it is fast.
Collections.synchronizedMapOne big lock. Simple, but slow when many threads write.
Plain HashMapOne thread only, or read-only after it is built.
RememberHashMap is a fast bicycle. ConcurrentHashMap is a bicycle with training wheels and a lock. Use the second one when two people ride.
