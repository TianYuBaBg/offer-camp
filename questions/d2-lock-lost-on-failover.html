Follow-up 05追问 05

Redis replication is asynchronous. The lock you just took may never reach the new master.Redis 主从是异步的。你刚拿的锁，可能根本没同步到新主。

Two clients then hold “the same” lock and both walk into the critical section. No lock library can prevent that — only the storage layer can.于是两个客户端同时“持”着同一把锁，双双进临界区。这没法靠锁库解决，只能靠存储层。

Short answer先给答案Async replication means an ack’d lock write can be lost on failover, so two holders may exist. Mitigate with a fencing token or keep the final guard in the database (unique index / conditional update).异步复制意味着已确认的加锁写入，切换后可能丢，于是可能出现两个持有者。缓解办法：fencing token，或者把最后一道防线留在数据库（唯一索引 / 条件更新）。

must know必背3 min3 分钟

01The exact failure失败是怎么发生的

1. C1 -> master: SET lock:order:1001 C1 NX PX 30000   -> OK
2. master crashes before replicating to the replica
3. replica promoted; the key is simply not there
4. C2 -> new master: SET lock:order:1001 C2 NX PX 30000  -> OK
5. C1 and C2 both believe they hold the lock

This is not a Redisson bug. It is the cost of using an in-memory store with asynchronous replication as a lock service.这不是 Redisson 的 bug，而是“用异步复制的内存库当锁服务”必然付的代价。

02Fencing token: make the loser harmlessfencing token：让输的那个无害

  • Every lock acquisition gets a monotonically increasing number (the fencing token).每次拿到锁都领一个单调递增的号（fencing token）。
  • Every write carries it: update sku_stock set qty = qty - 1, version = 12 where sku_id = 1001 and version < 12.每次写都带上它：update ... where ... and version < 12。
  • A stale holder's write is rejected by the storage layer, not by the lock.过期持有者的写入会被存储层拒绝，而不是靠锁拒绝。

This is the pattern Kleppmann argued for: the lock may be wrong, the write must not be.Kleppmann 争的就是这个：锁可以错，写入不能错。

03The cheaper version: let the DB decide更省事的版本：让数据库裁决

-- 扣库存：条件更新本身就是幂等闸门
update sku_stock set qty = qty - 1
 where sku_id = 1001 and qty >= 1;      -- 影响 0 行 = 卖完了

-- 一人一单：唯一索引兜底
insert into seckill_order(sku_id, user_id) values(1001, 7);  -- 重复直接拒绝

If the critical section is a single conditional update, you often do not need the distributed lock at all — and then failover cannot hurt you.如果临界区就是一条条件更新，常常根本不需要分布式锁——那主从切换也伤不到你。
