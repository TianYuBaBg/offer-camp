Every queue is a cache, not a ledger.队列只是缓存，不是账本。

Assume the delay message can be lost (Redis restart, failover, bug), so the DB must be able to find stale orders by itself.假设延迟消息会丢（Redis 重启、主从切换、代码 bug），所以数据库自己也要能找出超时单。

Short answer先给答案Daily compensation scan: find PENDING orders older than 35 minutes and close them through the same CAS path. Because closing is idempotent, double-processing is harmless — the scan is the safety net, the ZSet is the fast path.每日补偿扫描：找出超过 35 分钟还是 PENDING 的单，走同一条 CAS 关单路径。因为关单幂等，重复处理无害——ZSet 是快路，扫描是安全网。

must know必背3 min3 分钟

01The safety net安全网长什么样

-- 每天凌晨扫一次（走索引：status + create_time）
select order_no from orders
 where status = 'PENDING'
   and create_time < now() - interval 35 minute
 limit 500;

-- 逐条走同一套关单逻辑（锁 + CAS + 回补库存 + ZREM）
  • The scan is allowed to be slow — it runs once a day, not every second.扫描允许慢——一天一次，不是每秒。
  • 35 minutes, not 30: leave a grace window for in-flight callbacks.用 35 分钟而不是 30：给在途回调留容忍窗口。
  • Same code path as the fast path — one implementation, no drift.和快路走同一段代码——只有一份实现，不会走偏。
