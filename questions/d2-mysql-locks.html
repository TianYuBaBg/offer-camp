Follow-up 09追问 09

Every lock in MySQL, on three axes.MySQL 里到底有几种锁，各是什么意思。

Do not memorise the list. Hang it on three axes: granularity — who is locked; mode — how; idea — optimistic or pessimistic.别背名词。按三根轴搭骨架：粒度（锁谁）、模式（怎么锁）、思想（乐观还是悲观）。

Short answer先给答案Three levels of granularity: global, table (table lock, MDL, intention lock IS/IX), and row (record lock, gap lock, next-key lock, insert intention lock). Two modes: S shared and X exclusive. And the part that actually bites: row locks sit on index entries — no index, and you lock everything you scan.粒度三级：全局锁、表级（表锁、MDL 元数据锁、意向锁 IS/IX）、行级（记录锁、间隙锁、临键锁、插入意向锁）。模式两种：S 共享、X 排他。最要命的一句：行锁加在索引上——没走索引，锁的就是扫描到的所有行。悲观锁是 select ... for update，乐观锁是 where 带版本号的条件更新、看影响行数是 1 还是 0——两套写法，不是两把新锁。

01Three axes, one table三根轴，一张表

Axis轴Values取值What it means什么意思
granularity粒度global / table / row全局 / 表级 / 行级InnoDB's day job is row level; the other two show up in DDL and backupsInnoDB 日常用的是行级；另两级出现在 DDL 和备份场景

Interviewers start with “name the locks” and then drill into row locks. Answer the axes first, then the details — it shows you have a map, not a list.面试官通常先问“说说有哪些锁”，再往行锁里钻。先答三根轴，再补细节——说明你有地图，不是背清单。

02The four row locks行锁的四种形态

  • Record lock: locks one index record. A unique-index equality hit degenerates to exactly this.记录锁：锁住一条索引记录。唯一索引等值命中时，加的就是它。
  • Gap lock: locks the open interval between two index records, so it only blocks inserts.间隙锁：锁住两条索引记录之间的开区间，只拦插入，不拦别人读。
  • Next-key lock: record lock plus the gap in front of it. The default shape under RR, and what stops phantom reads.临键锁：记录锁加上它前面的间隙。RR 下的默认形态，防幻读靠的就是它。
  • Insert intention lock: taken on a gap before inserting, meaning “I am about to insert here”. It conflicts with gap locks held by others.插入意向锁：插入前在间隙上加，表示“我要往这里插”。它和别人的间隙锁冲突。

Gap locks only matter at RR and above. Under RC there is basically only the record lock — which is why RC sees fewer deadlocks and shorter lock waits.间隙锁只在 RR 及以上有意义。RC 下基本只有记录锁——所以高并发服务里 RC 的死锁和锁等待都更少。

03The three table-level ones表级的三把锁

  • Table lock (lock tables ... read/write): the whole table at once. A MyISAM-era tool that InnoDB rarely needs.表锁（lock tables ... read/write）：一次锁整表。MyISAM 时代的工具，InnoDB 很少主动用。
  • MDL metadata lock: added automatically. DML takes a read MDL, DDL takes a write MDL — so one long uncommitted transaction can block alter table, and everything queues behind it.MDL 元数据锁：自动加的。DML 拿读 MDL、DDL 拿写 MDL——所以一个长事务不提交，就能把 alter table 堵住，后面所有查询跟着排队。
  • Intention lock IS/IX: a table-level flag meaning “some row here is locked”. Without it, deciding whether a table lock is allowed would mean scanning every row.意向锁 IS/IX：表级的一个标志，说明“这张表里有行被锁了”。没有它，判断能不能加表锁得逐行扫。

04The one people get wrong: locks live on indexes最容易答错的一题：锁加在索引上

  • With an index, update orders set status = 'PAID' where order_no = 'T100' locks that one entry (or that range).有索引时，update orders set status = 'PAID' where order_no = 'T100' 只锁这一条（或这一段）。
  • Without an index, where remark = 'x' scans the whole table — and every scanned row gets locked. That is the “delete without a where clause” of the production world.没索引时，where remark = 'x' 全表扫描——扫到多少行就锁多少行。这就是线上版的“不带 where 的 delete”。
  • Debugging: show engine innodb status for LOCK WAIT, and information_schema.innodb_trx to find who is holding it.排查：show engine innodb status 看 LOCK WAIT，information_schema.innodb_trx 找谁占着锁。

A unique-index equality hit only needs a record lock — no gap. That is why “update one row by primary key” is the cheapest write you can make.唯一索引等值命中只需要记录锁、不加间隙。所以“按主键改一行”是你能写出的最便宜的写操作。

05Two statements you can say out loud乐观锁和悲观锁，各一句 SQL

begin;
select * from orders where id = 1 for update;   -- 悲观锁：这行被锁死，别人改要等
update orders set status = 'PAID' where id = 1;
commit;
update accounts
   set balance = balance - 100,
       version = version + 1
 where id = 1 and version = 3;   -- 影响 1 行 = 成功，0 行 = 冲突
  • Pessimistic: take the lock first, then read and write. for update adds an X record lock; if the row does not exist it becomes a gap lock, so a concurrent insert waits too.悲观锁：先锁住，再读再改。for update 加的是 X 记录锁；查不到那一行就退化成间隙锁，别人想插这个区间也得等。
  • Optimistic: no lock when reading; the version check happens in the same statement as the write. Affected rows = 1 means the version matched; affected rows = 0 means someone changed it first — re-read and retry.乐观锁：读的时候不加锁，版本校验和更新在同一条 SQL 里。影响 1 行说明版本对得上、改成功了；影响 0 行说明别人先改过，要重查再重试。
  • Choosing: low contention and cheap retries → optimistic; writes that must not fail → pessimistic; several rows or tables in one invariant → pessimistic plus a fixed lock order.怎么选：冲突少、重试便宜 → 乐观锁；写必须一次成功 → 悲观锁；一次要改多行多表 → 悲观锁加固定加锁顺序，避免互相等待成环。

An optimistic lock is not a database lock at all — it is a where condition. So it never deadlocks, but you own the retry loop, and version = version + 1 must sit in the same statement or the whole thing is a lie.乐观锁本质上不是数据库的锁，只是 where 里多了一个条件。所以它不会死锁，但重试要你自己写；而且 version = version + 1 必须和更新在同一条语句里，否则等于没校验。

06Say it like this面试这么说

Say it like this面试就这么说

Locks split into three granularities: global, table and row — InnoDB works at row level. Four row locks: record, gap, next-key, insert intention. RR takes next-key by default, which is what prevents phantom reads; RC is basically record locks only. At table level the two that matter are MDL and intention locks, and MDL is the main reason DDL and DML fight. The key point: row locks sit on index entries, so an update without an index locks everything it scans. And optimistic versus pessimistic is not two more locks: pessimistic is select for update, optimistic is a conditional update with a version in the where clause, judged by whether affected rows is 1 or 0.锁按粒度分三级：全局、表级、行级，InnoDB 日常用的是行级。行级有四种：记录锁、间隙锁、临键锁、插入意向锁；RR 下默认临键锁，防幻读靠的就是它，RC 下基本只有记录锁。表级里真正要记的是 MDL 和意向锁，MDL 是 DDL 和 DML 打架的主要原因。最关键的一点：行锁加在索引上，update 不走索引就会锁住扫到的所有行。乐观锁和悲观锁不是两把新锁：悲观锁就是 select ... for update，乐观锁是 where 里带版本号的条件更新，看影响行数是 1 还是 0。
