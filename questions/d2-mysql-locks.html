Follow-up 09追问 09

Every lock in MySQL, each with the SQL that takes it.MySQL 里到底有几种锁，每种用哪条 SQL 加出来。

Locks are not a vocabulary test. Each one has a statement that takes it, and a row in performance_schema.data_locks that proves it.锁不是背名词。每一种都有一条能把它加出来的 SQL，和一行能证明它的 data_locks 记录。

Short answer先给答案Three granularities: global, table (table lock, MDL, intention), row (record, gap, next-key, insert intention). Two modes S/X. Two ways to write it in code: pessimistic is for update / for share, optimistic is a version or a where condition. And the rule that decides everything: row locks sit on index entries, so an update without an index locks every row it scans.粒度三级：全局、表级（表锁、MDL、意向锁）、行级（记录、间隙、临键、插入意向）。模式两种 S/X。写法两种：悲观锁是 for update 或 for share，乐观锁是版本号或 where 条件。决定一切的一条：行锁加在索引上，update 不走索引就锁住扫到的所有行。

One rule keeps you out of trouble: gap and next-key only exist at RR and above. Under RC the same select takes only record locks — fewer deadlocks, more phantoms.一条能救命的规则：间隙锁和临键锁只存在于 RR 及以上。改成 RC，同一条 select 只加记录锁——死锁少、幻读多。

04Global lock, auto-inc lock, S versus X全局锁、自增锁、S 与 X

-- 全局锁：整库只读，备份用，线上不要开
flush tables with read lock;
unlock tables;

-- 自增锁：由 innodb_autoinc_lock_mode 决定（0 表级 / 1 默认 / 2 交错）
show variables like 'innodb_autoinc_lock_mode';

-- 共享锁 S：别人能读不能改
begin; select * from orders where id = 1 for share;

-- 排他锁 X：读写都要等
begin; select * from orders where id = 1 for update;
  • Global lock is a backup tool, not a business tool — production uses a logical dump or a replica instead.全局锁是备份工具，不是业务工具——线上用逻辑备份或从库备，不锁全库。
  • Auto-inc lock: mode 1 holds it until the statement ends; mode 2 interleaves and only guarantees uniqueness, which is safe when binlog_format is ROW.自增锁：模式 1 锁到语句结束；模式 2 交错分配、只保证不重复，binlog=ROW 时才安全。
  • S vs X: many for share can coexist and block every writer; one for update blocks both readers and writers.S 与 X：多把 for share 可以共存，但挡住所有写；一把 for update 读写全挡。

05The one that bites: locks live on indexes最容易答错：锁加在索引上

-- 有索引：只锁命中的那一行（或那一段）
update orders set status = 'PAID' where order_no = 'T100';

-- 没索引：全表扫，扫到多少行锁多少行
update orders set status = 'PAID' where remark = 'x';

-- 想知道到底锁了什么
select index_name, lock_type, lock_mode, lock_data
  from performance_schema.data_locks;
  • With no index the plan is a full scan, so every row it touches gets locked — the production version of “delete without a where”.没有索引就是全表扫，扫到的每一行都加锁——这就是线上版的“不带 where 的 delete”。
  • A unique-index equality hit needs only a record lock, no gap. That is why “update one row by primary key” is the cheapest write you can make.唯一索引等值命中只需要记录锁、不加间隙。所以“按主键改一行”是你能写出的最便宜的写操作。

06Pessimistic and optimistic, both in SQL悲观锁和乐观锁，两种写法

-- 悲观锁：先锁住再读再改（必须在事务里，否则语句结束锁就放了）
begin;
select * from orders where id = 1 for update;
update orders set status = 'PAID' where id = 1;
commit;

-- 乐观锁：读不加锁，版本校验和更新写在同一条语句里
update accounts
   set balance = balance - 100,
       version = version + 1
 where id = 1 and version = 3;   -- 影响 1 行成功，0 行冲突

-- 乐观锁的另一种写法：把业务约束写进 where（扣库存最常用）
update sku_stock set qty = qty - 1 where sku_id = 'A100' and qty >= 1;
  • Affected rows is the signal: 1 means the version matched, 0 means someone beat you — re-read and retry, never retry with the same version.影响行数就是信号：1 说明版本对上了，0 说明被抢先——要重查再重试，不能拿同一个版本号原地重试。
  • Watch out: affected_rows counts changed rows, not matched rows. If the value is unchanged you get 0 and misread it as a conflict — add useAffectedRows=true to the JDBC url.一个坑：affected_rows 算的是“真的改了”，值没变也返回 0，会被误读成冲突——JDBC 连接串加 useAffectedRows=true。
  • Pessimistic care: for update must be inside a transaction and must hit an index; when the row does not exist it takes a gap lock, which is more expensive.悲观锁的注意：for update 必须在事务里、必须命中索引；行不存在时加的是间隙锁，更贵。

07A deadlock you can build in two tabs两个窗口就能造出来的死锁

-- 会话 A                              -- 会话 B
begin;                                  begin;
update t set c = 1 where id = 1;        update t set c = 1 where id = 2;
update t set c = 1 where id = 2;        update t set c = 1 where id = 1;  -- 1213 死锁
  • Two transactions, two rows, opposite order — that is the whole recipe. InnoDB picks a victim and rolls it back with 1213, so the code must be able to retry.两个事务、两行数据、相反顺序——就这么多。InnoDB 挑一个牺牲者回滚并报 1213，所以代码里必须能重试。
  • Fix it by ordering: always take rows in the same order (by id ascending), or take one coarse lock instead of many fine ones.解法是定序：所有事务按同样顺序加锁（比如都按 id 升序），或者一次锁粗一点，别拿一堆细锁。
  • The scene is printed by show engine innodb status: both transactions and the two statements that collided.现场由 show engine innodb status 打印：两个事务和撞上的那两条语句。

08See it with your own eyes自己验证：三张表看锁

-- 当前持有哪些锁
select engine_transaction_id, object_name, index_name,
       lock_type, lock_mode, lock_status, lock_data
  from performance_schema.data_locks;

-- 谁在等谁
select * from performance_schema.data_lock_waits;

-- 打开锁日志，再看引擎状态里的 LOCK WAIT 段
set global innodb_status_output_locks = on;
show engine innodb status;

Do it once by hand: open two sessions, run for update in one, query data_locks in the other. The lock_mode strings you read there are exactly the rec_not_gap, gap, next-key and insert intention that interviewers ask about.手做一遍就记住了：开两个会话，一个 for update，另一个查 data_locks。里面 lock_mode 的字符串就是面试官问的 rec_not_gap、gap、临键、插入意向，不用背。

09Say it like this面试这么说

Say it like this面试就这么说

Locks split into three granularities: global, table and row; InnoDB works at row level. Row locks are record, gap, next-key and insert intention — RR takes next-key by default, which is what prevents phantom reads, and RC is basically record locks only. At table level the two that matter are MDL and intention locks, and MDL is why a long transaction blocks alter table. In code there are two ways: pessimistic is select for update inside a transaction and hitting an index; optimistic is an update with a version or a qty condition, judged by affected rows. And the key point: row locks sit on index entries, so an update without an index locks everything it scans.锁按粒度分三级：全局、表级、行级，InnoDB 日常用行级。行级有记录锁、间隙锁、临键锁、插入意向锁；RR 默认临键锁，防幻读靠它，RC 下基本只有记录锁。表级里真正要记的是 MDL 和意向锁，MDL 是长事务堵住 alter table 的原因。代码里两种写法：悲观锁是事务内的 for update 且命中索引；乐观锁是带版本号或 qty 条件的 update，看影响行数。最关键的一点：行锁加在索引上，update 不走索引就锁住扫到的所有行。
