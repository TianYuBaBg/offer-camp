Follow-up 06追问 06

Same disease, different delivery channel.同一个病，只是换了个投递渠道。

A queue guarantees “at least once”, never “exactly once”. So the consumer must be idempotent — the pattern is the same one you used for the payment callback.队列保证的是“至少一次”，不是“恰好一次”。所以消费端必须幂等——和你处理支付回调是同一套。

Short answer先给答案Duplicate consumption comes from ack loss, rebalance, producer retry, or manual re-delivery. Fix it in the consumer: a business unique key or a state machine — never rely on the queue to deliver once.重复消费来自 ack 丢失、rebalance、生产端重试、人工重投。在消费端解决：业务唯一键或状态机——不能指望队列“只投一次”。

02The consumer skeleton消费端骨架

@RabbitListener(queues = "order.paid")
public void onPaid(OrderPaidEvent e) {
    // ① 业务唯一键去重（和支付回调同一个思路）
    int n = mapper.insertIgnore(e.getBizNo());
    if (n == 0) { ack(); return; }        // 处理过，直接 ack

    // ② 状态机只允许往前走一步
    if (orderMapper.casToPaid(e.getOrderNo()) == 0) { ack(); return; }

    // ③ 真正的业务，本身也要幂等
    stockService.deduct(e.getSkuId());
    ack();

Two things must both be true: the message may repeat, and the handler must not care.两件事同时成立：消息可能重复，处理逻辑必须不介意。

03Do not do these别这么做

  • “The queue says it delivers once.” It does not. No mainstream MQ does.“队列说只投一次。”它没说。主流 MQ 都没有。
  • Deduplicating by message id only. The same business event may arrive with different ids.只按 message id 去重。同一个业务事件，id 可能不同。
  • Ack before the work finishes. A crash then loses the message for good.活没干完先 ack。崩了就永久丢消息。

04Say it like this面试这么说

Say it like this面试就这么说

所有 MQ 都是至少一次投递，重复来自 ack 丢失、rebalance、生产端重试。我们在消费端做幂等：业务唯一键插入去重，再走状态 CAS，最后业务本身也是条件更新。队列只管不丢，去重是消费方的责任。所有 MQ 都是至少一次投递，重复来自 ack 丢失、rebalance、生产端重试。我们在消费端做幂等：业务唯一键插入去重，再走状态 CAS，最后业务本身也是条件更新。队列只管不丢，去重是消费方的责任。
