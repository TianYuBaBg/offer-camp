Follow-up 02追问 02

The idempotent record proves it arrived. It proves nothing was finished.幂等记录只证明“来过了”，不证明“做完了”。

So a retry must be able to continue from wherever the last attempt stopped. That is the state machine's job.所以重试必须能从上次停下的地方接着做——这是状态机的活。

Short answer先给答案The idempotent table deduplicates. The order status says how far the work got. On retry: insert is rejected, read the status, then continue (PENDING), return success (PAID), or refund (CLOSED).幂等表负责去重，订单状态负责“做到哪一步”。重试时插入被拒，就看状态：还是 PENDING 就接着做，已经 PAID 就返回成功，CLOSED 就走退款。

01Four places it can die四个可能崩的点

Step步骤If it dies here崩在这里会怎样

Each row is a place a process can vanish. The rule: every step can be re-run safely, and “where am I” lives in durable storage, not in memory.每一行都是进程可能消失的地方。原则：每一步都能安全重跑，而“我做到哪了”要落在持久存储里，不在内存里。

02What the retry actually does重试时到底怎么走

-- 回调进来
insert into pay_idempotent(out_trade_no) values(?)   -- 被唯一键拒绝

-- 读取当前状态
select status from orders where order_no = ?

-- PENDING：上次没做完 → 继续（CAS 改状态、扣库存）
-- PAID   ：已经做完     → 直接回 success
-- CLOSED ：单已关       → 走退款

Never branch on “did I see this before”. Branch on “where is the order now”. The first is memory; the second is a fact.不要按“我之前见过没有”分支，要按“订单现在在哪一步”分支。前者是记忆，后者是事实。

03Why not one big transaction为什么不干脆一个大事务

  • Stock may live in Redis and shipping calls a third party. Neither joins a local transaction.库存可能在 Redis，发货要调第三方，两者都进不了本地事务。
  • Long transactions hold row locks and hurt throughput exactly when traffic is highest.长事务握着行锁，偏偏在流量最高的时候拖吞吐。
  • Even a perfect local transaction cannot cover “killed after commit, before the reply”.就算本地事务完美，也盖不住“提交后、回复前进程被杀”。
