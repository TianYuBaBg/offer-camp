说说 Java 中 HashMap 的原理？

必须会 Java 集合 口播 60 秒 追问 6 个

0130 秒版

先背这一段 · 再往下看 数组加链表，JDK 8 起冲突多了会树化。put 时先做 hash 扰动，再用 (n-1)&hash 定位桶：空桶直接放，冲突就比较 key，相同就覆盖，不同就挂在链表尾部；链表到 8 个、且容量到 64 就转红黑树。元素超过「容量 × 0.75」就扩容一倍，扩容时元素要么留在原位、要么挪到「原位 + 旧容量」。它不保证顺序、允许一个 null key、不是线程安全的。

02结构：一个数组，三种桶

HashMap 底层就是一个 Node<K,V>[] table。每个位置叫「桶」，桶里按冲突程度有三种形态：空、链表、红黑树。

  • Node：存 hash、key、value、next。key 和 value 都允许 null，但 null key 只有一个（hash 固定为 0，永远落在 0 号桶）。
  • TreeNode：红黑树节点，额外存父子指针和颜色；它同时保留 next，所以退化回链表时不用重建。
  • 顺序：完全不保证。要按插入顺序用 LinkedHashMap，要按 key 排序用 TreeMap。

03put 的六步

这是整道题的主干。面试时能把下面六个动作按顺序说完，基本就赢了一半。

if ((tab = table) == null || (n = tab.length) == 0)
    n = (tab = resize()).length;                  // ① 懒初始化：第一次 put 才建数组，默认 16
if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null);     // ② 定位桶，空桶直接放
else {
    if (p.hash == hash && (p.key == key || key.equals(p.key)))
        e = p;                                    // ③ 首节点就是同一个 key → 覆盖
    else if (p instanceof TreeNode)
        e = ((TreeNode<K,V>) p).putTreeVal(...);   // ④ 桶已树化 → 走红黑树插入
    else {
        for (int binCount = 0; ; ++binCount) {
            if ((e = p.next) == null) {
                p.next = newNode(hash, key, value, null);  // ⑤ 尾插（JDK 7 是头插）
                if (binCount >= TREEIFY_THRESHOLD - 1)
                    treeifyBin(tab, hash);                 //    到 8 → 尝试树化
                break;
            }
            if (e.hash == hash && (e.key == key || key.equals(e.key))) break;
            p = e;
        }
    }
    if (e != null) { V old = e.value; e.value = value; return old; }
}
++modCount;
if (++size > threshold) resize();                 // ⑥ 超阈值 → 扩容
return null;

① 先算 hash：扰动函数

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

把 hashCode 的高 16 位异或到低 16 位。因为定位桶时只用低几位，如果高低位分布不均，高位的信息就浪费了；异或之后高位信息也参与进来，碰撞显著减少。

② 定位桶：为什么是位运算

(n - 1) & hash 等价于 hash % n，但只有在 n 是 2 的幂时才成立。位运算比取模快，而且扩容时可以复用（见下一节）。

③④⑤ 冲突的三种处理

  • 同一个 key（hash 相等且 == 或 equals 相等）→ 覆盖 value，把旧值返回给调用方。
  • 桶里已经是树 → 按红黑树规则插入，O(log n)。
  • 桶里是链表 → 遍历到尾插；插完检查长度，到 8 就调 treeifyBin，但容量不足 64 时只会扩容、不会树化。

04扩容：为什么敢说「不用重算 hash」

元素个数超过 threshold = 容量 × 0.75 就扩容到 2 倍。经典说法是「扩容后所有元素重新取模」，这在 JDK 8 已经不成立：

// 旧容量 oldCap，新容量是它的 2 倍
// 每个节点只需回答一个问题：留在原位，还是挪到「原位 + oldCap」
if ((e.hash & oldCap) == 0)  loTail.next = e;   // 这一位是 0 → 留在原位 i
else                          hiTail.next = e;   // 这一位是 1 → 挪到 i + oldCap

因为容量是 2 的幂，扩容只是多出一个高位参与定位。所以 JDK 8 用 lo / hi 两条链把桶拆成两半，保持了原相对顺序，既不用重新计算 hash，也顺手消除了 JDK 7 头插带来的成环问题。

顺带提一句（加分项）：构造时传的初始容量不是最终大小。new HashMap<>(1000) 会经 tableSizeFor 向上取到最近的 2 的幂 —— 1024。所以想放 1000 个元素，正经写法是 new HashMap<>((int)(1000 / 0.75f) + 1)，一次性给够，避免中途扩容。

05两个数字：0.75 和 8，别搞混

这两件事经常被答成一件事，其实原因不同：

数字含义为什么是它
0.75负载因子，阈值 = 容量 × 0.75空间与冲突的折中。调小 → 桶用不满、扩容频繁；调大 → 冲突变多、查询退化。0.75 是通用平衡点。
8链表长度到 8 才考虑树化hash 均匀时链表长度近似泊松分布（λ≈0.5），到 8 的概率约 0.00000006。真到 8 说明冲突已经很不正常，此时转树把最坏 O(n) 降到 O(log n) 才划算。
64小于它只扩容、不树化小数组扩容很便宜，扩容比建树更划算；容量到 64 后才允许树化。
6树的节点少到 6 就退化回链表留出缓冲，避免在 7～8 之间反复树化/退化。

06线程安全：这是送分题，也是送命题

  • JDK 7：扩容用头插法，并发扩容可能让链表反向相接成环，之后 get 在环里打转，CPU 打满——这是最有名的 HashMap 事故。
  • JDK 8：改成尾插 + lo/hi 拆分，不会成环了，但并发 put 依然会互相覆盖、丢数据、size 不准。
  • 所以并发场景用 ConcurrentHashMap：JDK 8 用 CAS 尝试无锁插入，失败再 synchronized 只锁桶的头节点（锁粒度从整表降到单个桶），读操作靠 volatile 基本不加锁。
别说这句：「HashMap 加个 synchronized 就线程安全了」。面试官下一句就会问「那和 Hashtable 什么区别、和 ConcurrentHashMap 差在哪」——因为 Hashtable 正是整表加锁，性能差。

07追问六连

为什么容量必须是 2 的幂？

三个原因：

1）只有 n 是 2 的幂时，(n-1) & hash 才等价于 hash % n，位运算比取模快；

2）n-1 的二进制全是 1，hash 的每一位都能用上，桶的分布才均匀；否则有些位永远取不到，桶会被浪费；

3）扩容时多出来的正好是一个高位，元素要么留在原位、要么挪到原位 + oldCap，不用重新算 hash。

为什么负载因子是 0.75，不是 0.5 或 1？

它是空间和冲突的折中。太小（比如 0.5）：桶用不满，扩容次数翻倍，内存浪费；太接近 1：几乎每个桶都有冲突，链表变长，查询退化。

0.75 的额外好处是：容量 × 0.75 一定是整数、且不会让元素挤满整表，大部分业务场景下扩容次数和查询性能都够用。

注意别说：「0.75 是泊松分布算出来的」。泊松分布解释的是树化阈值 8，不是负载因子。

链表为什么到 8 才转红黑树？

理想哈希下，一个桶里的节点数服从泊松分布，参数 λ≈0.5。算下来长度到 8 的概率约 6×10⁻⁸——正常情况根本到不了。真到了 8，说明这个桶的 key 哈希冲突异常严重，链表查询 O(n) 已经拖慢性能，转树后是 O(log n)，用一点内存换时间，值得。

同时还有个前置条件：容量 ≥ 64。容量太小先扩容，因为扩容很可能就把冲突摊开了，比建树便宜。

JDK 7 的 HashMap 并发为什么会死循环？

两个线程同时 resize：线程 A 迁移到一半挂起，线程 B 迁完，A 醒来继续用自己的引用迁移——因为头插法每次把节点插到链头，两个线程交错执行后链表指针可能反向，形成 a → b → a 的环。之后任何 get 命中这个桶，就会在环里无限循环，CPU 直接 100%。

JDK 8 改尾插、且用 lo/hi 两条链整体搬迁，所以不会再成环；但并发写入的数据覆盖问题依然存在。

HashMap、Hashtable、ConcurrentHashMap 区别？

HashMap：非线程安全，允许一个 null key、多个 null value，性能最好，单线程或读多写少且外部同步时用。

Hashtable：整表 synchronized，不允许 null key/value，并发性能差，已经不推荐使用。

ConcurrentHashMap：JDK 8 用 CAS + synchronized 锁桶头节点，读基本无锁；不允许 null key/value（因为并发下 containsKey 之后仍可能变，null 会有歧义）。

为什么重写 equals 必须重写 hashCode？

put 分两步：先靠 hashCode 找桶，再靠 equals 判等。只重写 equals 的话，两个「相等」的对象 hashCode 不同，会落到不同的桶里，于是同一个 key 在 map 里出现两份，get 还可能取不到。

反过来只重写 hashCode 也不行：hash 相同、equals 不等，会挤在同一个桶里变成链表，等于人为制造冲突。

08照念稿（60 秒）

念到不磕巴 · 再填自己的例子

HashMap 本质是一个用 key 的 hash 定位的数组，数组每个位置叫桶。JDK 8 里桶内冲突了先挂链表，链表到 8 个、并且数组长度到 64，就转成红黑树，查找从 O(n) 变成 O(log n)。

put 的时候先算 hash：把 hashCode 的高 16 位异或到低 16 位，让高位也参与定位，减少碰撞；然后用 (n-1) & hash 找到桶——因为容量是 2 的幂，这个位运算等价于取模。

桶空就直接放；有东西就比较 key，相等就覆盖 value，不等就挂到链表尾部。

size 超过容量乘 0.75 就扩容一倍；因为容量是 2 的幂，扩容时每个元素要么留在原位、要么挪到原位加旧容量，不用重新算 hash。

它不是线程安全的：JDK 7 头插加并发扩容会形成环形链表，导致 get 死循环；JDK 8 改尾插不会成环了，但并发 put 依然会丢数据。所以并发场景用 ConcurrentHashMap，它用 CAS 加 synchronized 只锁桶的头节点。

10常见的答错

  • 只说「数组 + 链表」。JDK 8 必须补红黑树，否则会被追问「冲突特别多怎么办」。
  • 把头插说成 JDK 8 的行为。JDK 7 头插、JDK 8 尾插，这个顺序说反等于暴露没读过源码。
  • 「0.75 和 8 都是泊松分布算的」。泊松分布只解释 8；0.75 是空间/时间折中。
  • 「扩容后所有元素重新取模」。JDK 8 是 lo/hi 拆分，元素只可能原位或 +oldCap。
  • 「HashMap 线程安全」或「加 synchronized 就行」。并发要用 ConcurrentHashMap，且它的锁粒度是桶头节点。
  • 「null key 的 hash 是随机的」。是固定的 0，所以永远落在 0 号桶。
