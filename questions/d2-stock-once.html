One conditional update does both jobs.一条条件更新，同时解决“只扣一次”和“不超卖”。

`where qty >= 1` prevents overselling. Its idempotence comes from the caller: the deduction only runs after you have won the state transition.`where qty >= 1` 防超卖；它的幂等来自调用方——只有抢到了状态流转，才允许扣。

Short answer先给答案Oversell is prevented by the condition (qty >= 1 → 0 rows means sold out). Deduct-once is guaranteed by only deducting after the CAS to PAID succeeds — the second callback never reaches the deduction.防超卖靠条件（qty >= 1，影响 0 行就是卖完）；只扣一次靠“CAS 改状态成功之后才扣”——第二条回调根本走不到扣减那一步。

01Two guarantees, two mechanisms两个保证，两个机制

Goal目标Mechanism机制
never oversell不超卖where qty >= 1 + check affected rows条件 + 看影响行数
deduct once只扣一次only after CAS PENDING→PAID returns 1CAS 成功之后才扣
roll back on cancel取消回滚compensating update with the same condition同一条件的补偿更新

A conditional update is self-checking: it either changes one row or tells you why not.条件更新自带检查：要么改了一行，要么告诉你为什么不行。

02Redis first, DB lastRedis 先挡，数据库兜底

-- ① Redis 预扣（挡流量，不保证最终正确）
Long left = redis.decrement("stock:1001");   // < 0 就直接返回售罄

-- ② 数据库扣减（最终裁决）
update sku_stock set qty = qty - 1
 where sku_id = 1001 and qty >= 1;      // 0 行 = 真没了，回滚 Redis 并告警

-- ③ 取消/关单：把扣掉的加回去
update sku_stock set qty = qty + 1
 where sku_id = 1001 and order_no = ?;  -- 带订单号防重复回滚

Redis is the bouncer (fast, approximate). MySQL is the judge (slow, exact). Never trust the bouncer for the final count.Redis 是门卫（快、近似），MySQL 是法官（慢、精确）。最终数字绝不能只信门卫。

03The classic oversell story经典超卖怎么来的

  • Read qty, check in Java, then write qty-1. Two threads read 1, both write 0, both sold.先读 qty、在 Java 里判断、再写 qty-1。两个线程都读到 1，都写成 0，都卖出去了。
  • Fix: move the check into the WHERE clause so the database does it atomically.修法：把判断挪进 WHERE，让数据库原子地做。
  • Or lock the row (for update) — correct but slower, and it serialises the hot SKU.或者锁行（for update）——正确但更慢，而且把热点 SKU 串行化。
