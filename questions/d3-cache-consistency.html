Follow-up 01追问 01

Delete the cache, do not update it — and delete it twice.写完删缓存，不要更新缓存；而且要删两次。

Two concurrent writes can interleave so the older value lands in the cache last.两个并发写交错时，旧值可能最后落进缓存。

Short answer先给答案Cache Aside: read → miss → load from DB → put with TTL; write → update DB → delete cache. Why delete instead of update: update needs a value that may itself be stale from a concurrent read. Why twice: a reader that loaded before your commit can write the old value back after your delete, so delete once more ~500ms later (or via a delayed message).Cache Aside：读 → 未命中 → 查库 → 回填带 TTL；写 → 更新库 → 删缓存。为什么删不更新：更新要用值，而这个值可能来自并发读的旧快照。为什么删两次：读请求可能在提交前拿到旧值，在你删除之后又写回缓存，所以约 500 毫秒后再删一次。

01The interleaving that bites会咬人的交错

T1: update db  (value = 2)
T2: read db    (value = 1, still old snapshot)
T1: delete cache
T2: set cache = 1      <-- 旧值被写回，且不会自愈

-- 所以 500ms 后再删一次，把这段窗口压掉

This is also why “delete twice” is not paranoia — it is covering a specific interleaving.这也是“删两次”不是玄学的原因：它在盖一段具体的交错。

02When not to cache at all什么时候干脆别缓存

  • Money, stock, and anything the user compares against a bank statement: read the master.钱、库存、任何用户会拿去和流水核对的东西：直接读主库。
  • If the read is already fast and the write is frequent, the cache is pure overhead.读本来就快、写又频繁，缓存纯粹是负担。
  • Say the boundary out loud: “strong consistency paths do not go through the cache”.把边界说出来：“强一致的链路不走缓存”。
