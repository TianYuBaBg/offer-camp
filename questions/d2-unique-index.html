Follow-up 01追问 01

Why check-then-insert is broken, and the index is not.为什么“先查再插”有漏洞，而唯一索引没有。

The window is not in your code — it sits between two statements. The database closes it for you.漏洞不在你的代码里，而在两条 SQL 之间。数据库替你把这段窗口关掉了。

Short answer先给答案Two transactions can both see “not there yet” and both move on. The unique index does the conflict test inside the B+tree at insert time, atomically — so exactly one wins and the other gets a duplicate-key error.两个事务都能查到“不存在”，于是都往下走。唯一索引把冲突检测放进 B+tree、放进 insert 那一刻，是原子的——所以只有一个能成，另一个拿到 duplicate key。

must know必背3 min3 分钟

01The window you cannot see看不见的那段窗口

Under READ COMMITTED a plain select cannot see another transaction's uncommitted row, so “check” and “insert” are two separate moments with a gap between them.READ COMMITTED 下普通 select 看不见别人未提交的行，所以“查”和“插”是两个时刻，中间有缝。

T1: select * from pay_idempotent where out_trade_no = 'T100'   -- 空
T2: select * from pay_idempotent where out_trade_no = 'T100'   -- 也是空
T1: insert ...                                                  -- 成功
T2: insert ...                                                  -- 被唯一索引拒绝

-- 先查再插：两个都通过了检查，第二个插进去时才发现重复
-- 唯一索引把它变成数据库层的互斥，不需要你先查

Repeating the check inside a transaction does not help either. To make the check meaningful you would need select ... for update — a pessimistic lock. If you are going to lock anyway, the unique index is cheaper and harder to get wrong.在事务里再查一次也没用。要让“查”有意义，得 select ... for update 变成悲观锁——既然都要锁，唯一索引更便宜也更不容易写错。

02What the index actually does索引到底做了什么

  • InnoDB keeps the unique key in a B+tree. The insert walks to the leaf and must not find an equal key.InnoDB 把唯一键放在 B+tree 里。insert 走到叶子节点，必须找不到相同的键。
  • The check happens inside the insert — there is no gap for another session to sneak in.这个检查发生在 insert 内部——没有缝给别的会话钻。
  • The loser gets error 1062 (Duplicate entry) and can treat it as “someone else already owns this”.输的那个拿到 1062（Duplicate entry），可以直接当成“这份活已经有人认领”。

One statement, one decision. That is why it is the strongest layer you have.一条语句一个决定。这就是它比任何应用层判断都硬的原因。

03The code you actually write代码就这么写

try {
    mapper.insert(new PayIdempotent(outTradeNo, source));
} catch (DuplicateKeyException e) {
    return OK;              // 第二条回调：不干活，但必须回成功
}

-- 或者一条 SQL 搞定，用影响行数判断
insert into pay_idempotent(out_trade_no, source, created_at)
values(?, ?, now())
on duplicate key update source = source;   -- 0 行 = 重复

Both versions give you the same thing: a single statement whose result tells you whether you own this job.两种写法结果一样：一条语句，返回值就告诉你这份活归不归你。

04Where people get it wrong最容易踩的坑

  • Using the auto-increment id as the unique key. Use the business number (out_trade_no), or a retry slips straight through.拿自增 id 当唯一键。要用业务号（out_trade_no），否则重试能溜过去。
  • A composite unique key containing a nullable column. In MySQL, NULL is never equal to NULL — duplicates get in.联合唯一键里带可空列。MySQL 里 NULL 不等于 NULL，重复能溜进来。
  • Catching the duplicate and then not answering success. The platform keeps retrying for hours.捕到重复却不回成功。平台会一直重试，重试到明天。

05Say it like this面试这么说

Say it like this面试就这么说
