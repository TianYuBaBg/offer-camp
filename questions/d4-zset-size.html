Follow-up 04追问 04

Split the key by minute; never hold one giant ZSet.按分钟分 key，不要一个巨型 ZSet。

A single ZSet with millions of members is fine for range queries but expensive to inspect and impossible to expire per-shard.单个 ZSet 存几百万条，范围查询还行，但排查困难、也没法按片过期。

Short answer先给答案Shard by due-minute: order:delay:2026102905:37. Writes go to the shard; the poller only scans the current and previous minute shards, then deletes empty ones. Memory stays bounded and inspection stays easy.按到期分钟分片：order:delay:2026102905:37。写入进分片；轮询只看当前和上一分钟的分片，空了就删。内存有界，排查也容易。

must know必背3 min3 分钟

01Shard by minute按分钟分片

-- 入队
String shard = "order:delay:" + dueMinute(orderNo);   // yyyyMMddHHmm
redis.zadd(shard, dueMs, orderNo);

-- 轮询：只看这两个分片
for (String s : List.of(shardOf(now), shardOf(now - 60_000))) {
    ids = redis.zrangeByScore(s, 0, nowMs, 0, 100);
}

-- 分片空了就删，避免无限增长
if (redis.zcard(s) == 0) redis.del(s);

Also cap the batch (LIMIT 100): a million due at once should become ten thousand pulls, not one giant transaction.每批还要限额（LIMIT 100）：一次到期一百万，应该是一万次拉取，而不是一个巨型事务。
