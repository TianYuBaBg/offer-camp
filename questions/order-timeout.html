Question 4 · must know · orders and queues第 4 题 · 必背 · 订单与队列

An order is left unpaid for 30 minutes. How does it close itself?订单 30 分钟没付，怎么自动关掉？

A scheduled scan of the whole table melts the database. Something has to remember “this order is due at 10:47” — and be right when the payment callback arrives at the same second.每分钟扫一次全表会把数据库扫垮。得有个东西记住“这一单 10:47 到期”，还要在支付回调同一秒到达时不出错。

Short answer先给答案Put the order id into a Redis sorted set at checkout, with score = the due timestamp. A once-a-second job pulls what is due, takes a Redisson lock, and closes the order with a status CAS that also rolls the stock back. No RabbitMQ delay queue because the project already had Redis and a plugin or a TTL+DLX topology is extra machinery to run — the price is polling and no delivery guarantee, so a compensation scan and the CAS cover it.下单时把订单号塞进 Redis 的 ZSet，score 存到期时间戳；一个每秒跑的任务捞出到期的，先拿 Redisson 锁，再用状态 CAS 关单并回滚库存。不用 RabbitMQ 延迟队列，是因为项目里本来就有 Redis，而 TTL+DLX 或延迟插件是多一套要运维的东西；代价是轮询和不保证投递，所以加了补偿扫描和 CAS 兜底。

01Why not just scan the table every minute为什么不能每分钟扫全表

The naive version is one query: select id from orders where status='PENDING' and create_time < now() - interval 30 minute. Every minute. Forever.最朴素的写法就是一条 SQL：select id from orders where status='PENDING' and create_time < now() - interval 30 minute。每分钟一次，永远跑。

  • It scans rows that are not due yet — most of the table, most of the time.它扫的是还没到期的行——绝大多数时候，扫的是整张表。
  • The index only helps if you also store a “due at” column; with create_time + 30m the range is not sargable.索引只有在有“到期时间”这一列时才帮得上；用 create_time + 30 分钟 算出来的范围用不上索引。
  • Latency is up to one interval: an order can sit open for 30 minutes and 59 seconds.精度最差差一个周期：30 分 59 秒才发现该关。
  • In a flash sale, the scan and the business traffic fight for the same database.大促时，这个扫描和业务流量抢同一个数据库。

So the real requirement is not “scan often”, it is “wake me exactly when this order is due”.所以真正的需求不是“扫得勤”，而是“这一单到点时叫醒我”。

02Three ways to be woken up on time三条路，各自的代价

Approach做法Good好处Price代价
Scan the table定时扫全表Dead simple, no new component.最简单，不需要新组件。Database pressure, coarse precision, poor use of the index.压数据库、精度差、用不上索引。
MQ delay queueMQ 延迟队列Accurate, retries built in, dead-letter box.精度高，自带重试和死信。Another component to run; TTL+DLX or a plugin for RabbitMQ; you still must handle duplicate delivery.多一套中间件；RabbitMQ 要靠 TTL+DLX 或插件；重复投递还是得自己兜。
Redis sorted setRedis ZSetAlready in the project, one line to enqueue, second-level precision, one query to pull due items.项目里已有；入队一行代码；秒级精度；一条命令捞出到期的。Polling; no delivery guarantee — a failover can lose an entry, so you need a compensation scan.要轮询；不保证投递——主从切换可能丢条目，所以要补偿扫描。

The interview answer that scores: pick one, then say what you gave up and how you covered it. “We used Redis because we already had it; we covered the reliability gap with a nightly compensation scan.”能拿分的说法：选一个，然后说清放弃了什么、怎么补上。“选 Redis 是因为项目已有；可靠性缺口用每日补偿扫描兜住。”

03The whole mechanism is four lines整套机制就四行

-- at checkout: enqueue with the due time as score
ZADD order:delay  1730000000000  "SO20261029001"

-- every second: pull what is due
ids = ZRANGEBYSCORE order:delay  0  now   LIMIT  0  100

-- for each id: lock, check, close, remove
lock = redisson.getLock("lock:order:close:" + id)
if lock.tryLock():
    n = db.update("update orders set status='CLOSED' "
                 "where id=? and status='PENDING'", id)
    if n == 1: db.update("update sku_stock set qty=qty+1 where sku_id=?", skuId)
    redis.zrem("order:delay", id)
    lock.unlock()
  • score is the due timestamp — that is why a sorted set is the right structure: it is already sorted by time.score 就是到期时间戳——这就是为什么用有序集合：它本身按时间排好了。
  • LIMIT 100: never pull everything at once; a burst of 10k due orders becomes 100 batches instead of one long transaction.LIMIT 100：一次不捞太多；一万单到期变成 100 批，而不是一个长事务。
  • zrem only after success: if the process dies mid-way, the entry is still there and the next tick retries it.成功才 zrem：进程中途挂了条目还在，下一秒自然重试。
  • lock is per order: not one global lock, or you serialise every order in the system.锁按订单加：不要一把全局锁，否则全站订单排队。

04The two races you must name必须点名的两个竞态

Anyone can build the timer. The senior part is what happens when the callback and the timer land together.定时器谁都会做。真正分水平的是：支付回调和关单任务撞在同一秒时怎么办。

Race竞态Who wins谁赢What you do怎么做
Timer closes it, then the payment callback arrives关单先改成功，支付回调后到The order is already CLOSED, so the CAS updates 0 rows.订单已是 CLOSED，CAS 影响 0 行。Money arrived for a closed order — refund, and say it out loud in the interview.钱到了但单子关了——走退款，面试时要把这句话说出来。
Callback marks it PAID, then the timer fires回调先改成 PAID，定时任务后到The CAS condition status='PENDING' fails, so the timer does nothing.CAS 条件是 status='PENDING'，不成立，定时任务什么都不做。

Both directions are handled by the same where status='PENDING'. That is why the interview answer must include the CAS even though the question is about a timer.两个方向都被同一个 where status='PENDING' 挡住了。所以哪怕问的是定时器，答案里也必须带 CAS。

And the second race: two app instances polling the same Redis. Both see the same order id.第二个竞态：两个实例轮询同一个 Redis，同时捞到同一个订单号。

  • The distributed lock makes only one of them work on it.分布式锁让只有一个实例真的去处理。
  • Even if the lock is lost (failover), the CAS still makes the second one a no-op.就算锁丢了（主从切换），CAS 也会让第二个变成空操作。
  • Two layers, and neither of them is “I added a lock, done”.两层，而且都不是“我加了把锁就完事”。

05Four follow-ups, one line each四个追问，一句话一个

Follow-up追问One-line answer一句话答案
Why not sleep a thread for 30 minutes?为什么不直接 sleep 30 分钟？One thread per order; 100k orders is 100k threads, and a restart loses them all.一单一个线程；十万单就是十万个线程，重启全丢。
What if an entry is lost from Redis?Redis 丢了条目怎么办？A daily compensation scan over PENDING orders older than 30 minutes — it is the safety net, and it is allowed to be slow.每天一次补偿扫描，捞 30 分钟前还没结束的 PENDING 单——它是安全网，可以慢。
What about the RabbitMQ delay queue?RabbitMQ 的延迟队列怎么做？Two ways: per-message TTL + dead-letter exchange, or the delayed-message plugin. The first has head-of-line blocking; the second is an extra plugin.两种：消息 TTL + 死信交换机，或延迟插件。前者会队头阻塞，后者要装插件。
100k due at once?十万单同时到期？Bit by minute: keys like order:delay:2026102910:47, and enqueue batch updates.按分钟分桶：order:delay:2026102910:47，入队用批量写。

0660-second script60 秒照念稿

Read this out loud照这段说，60 秒

We do not scan the table. At checkout the order id goes into a Redis sorted set with the due timestamp as the score; a job runs once a second, pulls up to 100 due ids, and for each one takes a Redisson lock, closes it with an update whose where-clause is status='PENDING', rolls the stock back, and only then removes the entry from the set. The where-clause is the important part: if the payment callback already marked it paid, the update touches 0 rows and we do nothing; if we closed it first and the callback arrives after, the money is there for a closed order and we refund. We chose this over a RabbitMQ delay queue because the project already had Redis and adding TTL+DLX or the delayed-message plugin is another thing to operate. The trade-off is polling and no delivery guarantee, so there is a daily compensation scan over stale pending orders, and the CAS makes a double close harmless.我们不扫表。下单时把订单号写进 Redis 有序集合，score 存到期时间戳；一个每秒跑的任务一次捞最多 100 个到期的 id，逐个加 Redisson 锁，用 where 条件里带 status='PENDING' 的更新去关单、回滚库存，成功后才从集合里删掉。 那个 where 条件是关键：如果支付回调已经把它改成已支付，这条更新影响 0 行，我们什么都不做；如果我们先关了、回调后到，钱到了但单子已关，就走退款。 没选 RabbitMQ 延迟队列，是因为项目里本来就有 Redis，而 TTL+DLX 或延迟插件是多一套要运维的东西。代价是轮询和不保证投递，所以加了每天一次的补偿扫描，并且用 CAS 让重复关单变得无害。

07Where this sits on my résumé怎么挂到我自己的项目上

One line on the résumé, four things you can now defend:简历上只有一行，现在你能守住四件事：

  • The line: “用 Redis 延时队列做订单超时关单，替代轮询：超时 30 分钟自动取消并回滚库存”.原句：“用 Redis 延时队列做订单超时关单，替代轮询：超时 30 分钟自动取消并回滚库存”。
  • Why not scan: index, pressure, one-cycle latency.为什么不扫表：用不上索引、压库、差一个周期。
  • Why not MQ: the project already had Redis; TTL+DLX or a plugin is extra machinery.为什么不用 MQ：项目已有 Redis；TTL+DLX 或插件是多出来的运维。
  • How it stays safe: per-order lock + status CAS + daily compensation scan.怎么保证不出错：按单加锁 + 状态 CAS + 每日补偿扫描。

订单系统和好气网都用了 Redisson, so “I know Redisson” is already on the résumé — this question is where it turns from a keyword into a mechanism.订单系统和好气网都写了 Redisson，所以“我会 Redisson”本来就在简历上——这道题就是把那个词变成机制的地方。

08Three things not to say三句别说

  • “I run a scheduled job every minute.” — Then you scan the whole table; say how you avoid it.“我起个定时任务每分钟跑一次。”——那就是扫全表；要说出你怎么避免。
  • “Redis is reliable, so nothing is lost.” — A failover can drop entries; name the compensation.“Redis 很可靠，不会丢。”——主从切换会丢；要说出补偿。
  • “The lock guarantees it closes once.” — Locks fail; the CAS is what makes it once.“加锁就能保证只关一次。”——锁会失效；保证“只关一次”的是 CAS。
